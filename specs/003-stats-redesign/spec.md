# Feature Specification: Statistics Period Tabs, Daily Drill-Down, Phosphor Tag Icons, Control-Button Tooltips

**Feature Branch**: `003-stats-redesign`
**Created**: 2026-05-12
**Status**: Draft
**Input**: User description: "A UI rework of the statistics surface and tag-icon set, plus small ergonomic improvements. Replace the single-period Calendar & Statistics view with a Daily/Weekly/Monthly/Yearly period-tabbed view backed by one reusable bar-chart component; add a separate top-level Daily drill-down (month grid + sessions timeline for the selected day); extend the tag icon picker with nine Phosphor glyphs (replacing the five emoji entries while keeping `ri-brain-line` as the default); add CSS-driven tooltips with state-aware text to the timer control buttons. All UI-side; the engine and Tauri bridge are untouched. VISION.md's 'see the history' workflow is the justification — Statistics is for trends, Daily is for 'what did I do on this specific day'."

## Clarifications resolved

- 2026-05-12: Phosphor font is **vendored locally** via Trunk's `copy-dir`, not loaded from a CDN. The e2e suite's `_blockExternal` fixture blocks remote font fetches, and `src/index.html` already vendors remixicon the same way (`<link data-trunk rel="copy-dir" href="assets/icons" data-target-path="assets/icons">` + a same-origin stylesheet at `/assets/icons/remixicon.css`). Phosphor follows the same pattern: assets land under `assets/icons/phosphor/`, the CSS is loaded from a same-origin URL, and the chromium-linux baseline renders deterministically without network. CSP and `_blockExternal` are preserved — no exemptions added.
- 2026-05-12: Control-button tooltips use CSS-driven `data-tooltip` (a styled hover/focus tooltip) **in addition to** the native `title=` and `aria-label=` attributes that already exist on `#stop-btn`, `#play-pause-btn`, and `#skip-btn` (verified at `src/src/components/timer/mod.rs:1556-1605`). `title=` stays for native-tooltip + accessibility-tree parity; `aria-label=` is the assistive-tech contract; `data-tooltip` is the visible UI tooltip that survives keyboard-focus state and theme styling. Per the CHK041 entry below, the verbose `aria-label` / `title` pair and the terse `data-tooltip` are intentionally **decoupled** (different strings per state, both derived from the same engine-state source so drift is impossible).
- 2026-05-12: Statistics view's Weekly variant preserves the existing e2e selector contract (`#prev-week`, `#next-week`, `#week-range`, `#prev-month`, `#next-month`, `#current-month`, `#calendar-grid`, `#focus-summary-card`, `#total-focus-week`, `#avg-focus-day`, `#weekly-sessions`, `#sessions-table-body`); Daily/Monthly/Yearly variants get new selectors (`#prev-day`, `#next-day`, `#day-range`, `#prev-month-period`, `#next-month-period`, `#month-range`, `#prev-year`, `#next-year`, `#year-range`, plus `#hourly-chart`, `#monthly-chart`, `#yearly-chart`). The legacy `#weekly-chart`, `#daily-chart`, `#today-focus-time`, `#weekly-focus-time` selectors are **migrated in-cycle** (per Acceptance Scenarios, not deferred) — they survive on the Weekly variant of the new period UI under the same IDs, with the brief's spurious `#today-focus-time` reference noted as a non-existent selector (it does not appear in any current e2e spec; verified by grep).
- 2026-05-12: The new top-level "Daily" sidebar entry adds a fourth nav icon between Calendar and Settings. The existing Calendar nav button is **renamed in intent** ("Statistics") but its `id="calendar-nav"`, route `data-view="calendar"`, and the inner view's `id="calendar-view"` are preserved (e2e contract; `_smoke.spec.js:20` asserts `#calendar-view` initially hidden). Sidebar icons swap glyphs (Calendar → `ph-chart-line-up`, new Daily → `ph-calendar-check`) but the selector surface stays stable. The view title text changes from "Calendar & Statistics" to "Statistics".
- 2026-05-12: The "sidebar gradient" referenced in the brief is the `box-shadow: 2px 0 20px color-mix(in srgb, var(--*-color) 15%, transparent)` glow on `.sidebar` (verified at `src/style/sidebar.css:18,25,30,35`) — not a CSS `linear-gradient()`. The constraint is normative: this feature MUST NOT introduce a `border-right` on `.sidebar`, a 1px separator element between sidebar and `.main-content`, or any rule that flattens the existing per-mode shadow into a hard edge. Theme overrides preserve the same shadow shape.
- 2026-05-12 (CHK040, Principle **IV. Visual Regression Is The UI Contract**): The Statistics view's four period variants (Daily / Weekly / Monthly / Yearly) MUST be captured as **four separate visual-regression baselines** — not collapsed to one Weekly frame. Each period is a materially different layout (24-hour bars vs 7 day-bars vs 28–31 day-bars vs 12 month-bars + different navigator widgets); one baseline cannot catch a regression specific to e.g. the Monthly bar chart's tick spacing. Per-baseline justification notes in the PR description handle the budget concern. Verified against `tests/e2e/visual-regression.spec.js` (one linear test, baselines added by appending `await expect(page).toHaveScreenshot(...)` calls — trivially extensible) and `tests/e2e/playwright.config.js:11-29` (`fullyParallel: true`, `maxDiffPixelRatio: 0.02` — no per-frame cost cliff). FR-043 is amended to require, not just permit, the four per-period frames.
- 2026-05-12 (CHK041, Principle **III. Type Safety Over Defensive Code** + WCAG SC 4.1.2 *Name, Role, Value*): Control-button `aria-label=` strings MUST remain verbose ("Reset timer" / "Undo last session" / "Start or pause timer" / "Skip session"); only `data-tooltip=` is shortened for tooltip-fit ("Reset" / "Undo" / "Start" / "Pause" / "Resume" / "Skip session"). Decoupling the accessible name from the visible tooltip preserves screen-reader informativeness while letting the visual chrome stay compact — there is no WCAG requirement that the accessible name match the visible tooltip text when both are present. The "same Leptos signal" invariant from FR-026 now binds two signals per button (one verbose `aria-label`/`title`, one terse `data-tooltip`); both derive from the same `engine.current_mode()` + run-state source so per-state drift is still impossible. Verified at `src/src/components/timer/mod.rs:1556-1605` (existing verbose strings: `aria-label="Reset timer"` / `"Undo last session"` / `"Start or pause timer"` / `"Skip session"`).
- 2026-05-12 (CHK042, Principle **VIII. Spec-Driven Feature Flow**): The per-period tag-usage pie is **static-only in v1**. Click-to-cross-filter (hovering or clicking a pie slice highlights matching bars in the bar chart above) is a deferred follow-up because cross-filtering carries its own UX surface — drill-down semantics, keyboard navigation, screen-reader announcement of filter state, "clear filter" affordance — that deserves its own spec, not a footnote here. New **FR-050** in the Out-of-scope guards section records this; the follow-up issue is tracked separately if requested later.
- 2026-05-12 (CHK043, Principle **III. Type Safety Over Defensive Code** + Principle **IV. Visual Regression Is The UI Contract**): The off-viewport `#sessions-table-body` block (currently at `src/src/components/calendar.rs:644+`, rendered off-viewport per the comment at `calendar.rs:640-643`) **moves to the new Daily view's right column** alongside the Sessions Timeline. Statistics becomes a pure trend/aggregate surface; Daily becomes the single source of truth for "what happened on this specific day" — duplicating the DOM would create two "today's sessions" surfaces and risk drift. The e2e contract at `tests/e2e/sessions-history.spec.js:31-37` is bound to the Calendar tab — `tapTab(page, "Calendar")` followed by `page.locator("#sessions-table-body")`. The migration path: update that one line to `tapTab(page, "Daily")` in the same PR; the selector string `#sessions-table-body` is preserved (no rename, no DOM-shape change). Bundle B amends **FR-019** to relocate (not just remove) the off-viewport sessions table; **A20** is overridden by this clarification.

## User Scenarios & Testing *(mandatory)*

> This feature is **five user-facing bundles** (Bundle A — Statistics period tabs + reusable bar chart; Bundle B — Daily drill-down view; Bundle C — Phosphor tag icons; Bundle D — control-button tooltips; Bundle E — PeakFocusTime line chart [optional / cut-line]). Bundles A and B together replace the prior single-period Calendar & Statistics view; the rest are independent. Constitutional anchors are cited inline by name and number.

### User Story 1 - Switching periods to see how focus trends across timescales (Bundle A, Priority: P1)

A user opens the Statistics view (the renamed-from-"Calendar & Statistics" tab — same `#calendar-nav` button) and sees a row of period tabs at the top: **Daily**, **Weekly** (default, matching pre-rework behaviour), **Monthly**, **Yearly**. Clicking each tab swaps the bar-chart panel and the period-navigator widget to that period's scale. Daily shows 24 hourly bars (00:00–23:00) with a fixed 60-min/hour ceiling; Weekly shows 7 day-bars with a Weekly ≥ 20 min dynamic floor; Monthly shows 28–31 day-bars with a ≥ 50 min floor; Yearly shows 12 month-bars with a ≥ 100 min floor. The same panel renders the active period's tag-usage breakdown (pie + legend) below the bar chart.

**Why this priority**: Headline user benefit of the bundle — "did I actually do focused work this week / month / year" is the VISION.md "see the history" workflow promoted from a single weekly summary to a four-period decision surface. Tied to **II. Local-Only** (every metric is read from the existing `load_sessions`/`load_tags` outputs — no new network egress), **III. Type Safety Over Defensive Code** (period is a closed `enum Period { Daily, Weekly, Monthly, Yearly }`, not a string), and **VI. The Tauri Boundary Is Stable** (no new Tauri commands; no new IPC).

**Independent Test**: With seeded session data spanning today, this week, this month, and this year, navigate to Statistics. Click each period tab in turn. Verify the bar chart re-binds to the new period's bar count and label set, the navigator widget swaps its prev/next labels (← Yesterday / Today → for Daily; ← Last week / This week → for Weekly; etc.), and the tag-usage breakdown re-computes against the new period's session set. Verify Weekly is selected on cold load.

**Acceptance Scenarios**:

1. **Given** the Statistics view freshly opened, **When** the user looks at the top of the view, **Then** four period tabs are visible — Daily / Weekly / Monthly / Yearly — with **Weekly** selected by default (matching pre-rework cold-start behaviour).
2. **Given** Weekly is selected, **When** the user clicks the **Daily** tab, **Then** the bar chart re-renders with 24 hourly bars (labelled `00:00`, `02:00`, `04:00`, ..., `22:00` per CSS-driven label density), the navigator widget shows `← Yesterday` / `Today →` labels and a `#day-range` label like `"May 12 2026"`, and the tag-usage breakdown re-computes against the current day's sessions.
3. **Given** Daily is selected, **When** the user clicks the **Monthly** tab, **Then** the bar chart re-renders with 28–31 day-bars (one per day of the current month), the navigator shows `← Previous month` / `Next month →`, and the tag-usage breakdown reflects the current month.
4. **Given** Monthly is selected, **When** the user clicks the **Yearly** tab, **Then** the bar chart re-renders with 12 month-bars labelled Jan–Dec, the navigator shows `← Previous year` / `Next year →`, and the tag-usage breakdown reflects the current year.
5. **Given** any period selected with a non-empty session set, **When** the bar chart renders, **Then** every bar's height is proportional to the period's metric (focus minutes for that hour/day/month), the period's maximum value defines the chart's 100% line subject to the per-period floor (Daily fixed 60; Weekly ≥ 20; Monthly ≥ 50; Yearly ≥ 100 minutes), and an empty period renders all bars at the configured minimum-visible-height floor (no zero-height bars).
6. **Given** a navigator at the period's "current" cursor (today / this week / this month / this year), **When** the user clicks the prev-arrow, **Then** the cursor decrements by one period unit and the bar chart re-binds against the new cursor's session set. **When** they click next, **Then** the cursor increments.
7. **Given** the user is on Daily/Monthly/Yearly and clicks a different period tab, **When** the period swaps, **Then** the cursor resets to the period's "current" anchor (today / this week / this month / this year) — cursor state is not preserved across period swaps.
8. **Given** the bar-chart component implementation, **When** a developer inspects the code, **Then** Daily/Weekly/Monthly/Yearly all instantiate the **same reusable `BarChart` component** parametrised by `{max_scale, x_axis_labels, bar_values}` — four bespoke chart implementations is forbidden.

### User Story 2 - Drilling down into a specific day's sessions (Bundle B, Priority: P1)

A user wants to know "what did I do last Tuesday". From the sidebar, they click the new **Daily** entry (a fourth nav icon, between Calendar/Statistics and Settings). The view loads with a month-grid calendar on the left (same visual shape as the old mini-calendar in `CalendarView`) and a Sessions Timeline panel on the right showing today's sessions. The user clicks a different day in the grid; the right panel re-binds to that day's session set, showing each session as a positioned block on a 00:00–24:00 horizontal timeline (mirroring the existing `#sessions-timeline` shape). The selected day's cell gets a saturated highlight; the day-of-week header row uses Sunday-first (matching the existing baseline at `src/src/components/calendar.rs:553-561`).

**Why this priority**: Daily-drilldown is the second half of the rework — Statistics shows trends across periods, Daily answers "what specifically did I do that day". Without Bundle B, the user can never click into a single day; the period-tab Daily variant is for distribution-by-hour, not session-by-session. Tied to **II. Local-Only** (reads existing `load_sessions` output), **III. Type Safety Over Defensive Code** (selected-day cursor is `DateTime<Utc>`, not a date-string), and **IV. Visual Regression Is The UI Contract** (Daily view is a new screen with no prior baseline — adds exactly one baseline `daily-chromium-linux.png`).

**Independent Test**: With seeded sessions on multiple days of the current month, navigate to Daily. Verify today is selected by default and the timeline shows today's sessions. Click a different day in the grid. Verify the timeline re-binds and the selected-day highlight follows the click. Click a day with no sessions. Verify the timeline shows the "No sessions completed" empty state. Click `← Previous month` / `Next month →`; verify the grid navigates and the selected-day cursor persists if the day exists in the new month, otherwise falls back to the first of the new month.

**Acceptance Scenarios**:

1. **Given** the sidebar after Bundle B ships, **When** the user looks at the nav strip, **Then** four icons are present in order: Timer (`id="timer-nav"`, unchanged), Statistics (the renamed Calendar nav, `id="calendar-nav"`), Daily (new, `id="daily-nav"`, `data-view="daily"`), then the Settings nav-large at the bottom. (Tasks nav exists in `app.rs` but is not part of the visible sidebar in the current build; this rework does not change that.)
2. **Given** the Daily nav button, **When** the user clicks it, **Then** the route resolves to a new view container `id="daily-view"`, the other `*-view` containers gain `.hidden`, and the Daily view renders a two-column layout with the month grid on the left and the sessions timeline on the right.
3. **Given** Daily view freshly opened, **When** the user looks at the grid, **Then** today's cell carries `aria-current="date"` (matching the existing convention), the grid uses Sunday-first day-of-week headers (matching `src/src/components/calendar.rs:553-561`), and the timeline panel shows today's sessions.
4. **Given** a session-bearing day cell, **When** the user clicks it, **Then** the right panel's `<h4 id="selected-day-title">` text updates to that day's label (e.g., `"Tuesday, May 5 2026"`), the timeline re-binds to that day's sessions, and the clicked cell receives a `selected` modifier class (visually distinct from the today-cell highlight when they're different cells).
5. **Given** a day with zero sessions, **When** the user selects it, **Then** the timeline shows the empty-state "No sessions completed" label (mirroring the current calendar's empty-state at `src/src/components/calendar.rs:625-628`).
6. **Given** the user clicks `← Previous month` / `Next month →` on the Daily view's calendar header, **When** the cursor moves, **Then** the grid re-renders for the new month and the selected day rolls to the same day-of-month in the new month if it exists (e.g., May 12 → Apr 12); if the new month is shorter (e.g., Jan 31 → Feb), the selected day clamps to the last day of the new month.
7. **Given** the Statistics view's old right-column mini-calendar + Today's Sessions panel (currently at `src/src/components/calendar.rs:542-635`), **When** Bundle B ships, **Then** that block is **removed from Statistics** — the right-column duplication is the rework's primary cleanup, since Daily is now the dedicated home of that interaction.

### User Story 3 - Picking a Phosphor icon for a new tag (Bundle C, Priority: P2)

A user opens the tag picker (in the timer view's `#timer-status` row dropdown) and clicks "+ New Tag" to create one. The icon-selector dropdown shows the existing default `ri-brain-line` plus eight more options — three from remixicon (`ri-focus-3-line`, `ri-lightbulb-line`) **and nine new Phosphor icons** (e.g., `ph-butterfly`, `ph-cloud`, `ph-code-simple`, `ph-github-logo`, `ph-apple-logo`, `ph-crown-simple`, `ph-atom`, `ph-student`, `ph-cpu`). The five legacy emoji entries (`🧠 🎯 ⚡ 🔥 💪`) are **removed from the picker** but remain valid in the renderer (any existing tag persisted with an emoji icon continues to render as that emoji). The user picks `ph-cloud`, names the tag "Cloud Work", and saves; the tag list shows the new tag with the cloud glyph rendered via `<i class="ph ph-cloud"></i>`.

**Why this priority**: The icon set is the most visible part of the tag UI — Phosphor icons are visually richer and more on-brand than the emoji that ship from the system font (which renders inconsistently across OS / theme combos and is the reason `DEFAULT_NEW_TAG_ICON` is already `ri-brain-line`, not `🧠`, per the comment at `src/src/components/timer/mod.rs:86-92`). P2 because it's a picker-only ergonomic improvement — independently demoable, no engine impact, no data migration. Tied to **III. Type Safety Over Defensive Code** (icon-name parsing dispatches on a typed-prefix match `ri-` / `ph-` / grapheme — no stringly-typed branching) and **IX. Lock Files Are First-Class** (the Phosphor webfont is vendored locally; no new Cargo or npm runtime dependency is added — assets are bundled via Trunk's `copy-dir`).

**Independent Test**: Open the tag picker, click "+ New Tag", verify the icon selector shows 12 icons total: 3 remixicon (`ri-brain-line` default, `ri-focus-3-line`, `ri-lightbulb-line`) + 9 Phosphor. Verify the 5 emoji entries are absent from the picker. Create a tag with `ph-cloud`; verify it renders correctly. Seed a tag with `\u{1f9e0}` (brain emoji) into the on-disk tag store; verify it loads and renders as the raw glyph (renderer fallback for non-`ri-`/non-`ph-` prefixes).

**Acceptance Scenarios**:

1. **Given** the tag-creator dropdown (`#icon-selector-dropdown`), **When** the user opens it, **Then** exactly 12 icon options are visible: 3 remixicon entries first (`ri-brain-line`, `ri-focus-3-line`, `ri-lightbulb-line`), then 9 Phosphor entries (`ph-butterfly`, `ph-cloud`, `ph-code-simple`, `ph-github-logo`, `ph-apple-logo`, `ph-crown-simple`, `ph-atom`, `ph-student`, `ph-cpu`). No emoji.
2. **Given** the icon selector with the default selected (`ri-brain-line`), **When** the user clicks a Phosphor entry (`ph-cloud`), **Then** the `#selected-icon-btn` preview re-renders with `<i class="ph ph-cloud">` and the `new_tag_icon` signal holds the string `"ph-cloud"`.
3. **Given** the user saves a tag with `icon = "ph-cloud"`, **When** the tag list re-renders, **Then** the new tag's icon cell renders `<i class="ph ph-cloud">` and a wasm-bindgen-test verifies the DOM contains both the `ph` wrapper class and the specific glyph class.
4. **Given** a pre-rework `tags.json` containing a tag with `icon = "\u{1f9e0}"` (brain emoji), **When** the new build loads it, **Then** the tag deserialises unchanged and renders as the raw glyph (the rendering function's typed-prefix dispatch falls through to "emit as text content" for inputs that match neither `ri-*` nor `ph-*`).
5. **Given** an icon-name input to the renderer, **When** the dispatch decides how to render, **Then** the branching is on a typed prefix-match enum (e.g., `enum IconClass { Remix(&str), Phosphor(&str), Glyph(&str) }`) — not a chain of `if name.starts_with(...)` string checks. (Principle III.)
6. **Given** the timer view's `#status-icon` element (drives the active-tag's icon in the mode badge), **When** the active tag's icon is a Phosphor name, **Then** the `<i>` element carries `class="ph ph-<glyph>"`; when it's a remixicon name, `class="ri-<glyph>"`; when it's a raw glyph, the `<i>` contains the grapheme as text. The existing fallback `"ri-brain-line"` for "no active tag in Focus" is preserved.

### User Story 4 - Hovering or focusing a control button to confirm what it does (Bundle D, Priority: P2)

A user hovers the **Stop/Reset/Undo** button (`#stop-btn`) during a focus session. A small styled tooltip appears below the button reading **"Reset"**. The user completes the focus session; the timer transitions to break mode. They hover the same button again; the tooltip now reads **"Undo"** (because in Break/LongBreak mode the button undoes the last completed pomodoro per the existing handler at `src/src/components/timer/mod.rs:974-993`). Similarly, the Play/Pause button reads "Start" when idle, "Pause" when running. Skip reads "Skip session" (no state variants). Keyboard-focusing each button triggers the same tooltip — the tooltip is not pointer-only.

**Why this priority**: The control buttons today carry `aria-label=` and `title=` (verified at `mod.rs:1556-1605`) which means assistive tech and the browser's native hover-delay tooltip already cover both. What's missing is a **styled, keyboard-focus-triggered tooltip** that matches the rest of the app's visual language and surfaces fast (no 1-second native-tooltip delay) on both pointer hover AND keyboard focus. P2 because it's polish — independently demoable, no engine impact, no data migration. Tied to **III. Type Safety Over Defensive Code** (tooltip text is a derived signal off `engine.current_mode()` and `engine.is_running()` — same source-of-truth as the existing `title=` / `aria-label=`; no second copy to keep in sync at risk of drift).

**Independent Test**: Open the timer view in Focus mode. Hover `#stop-btn`; verify the CSS-driven tooltip shows "Reset". Complete the focus session (skip or tick to zero). Hover `#stop-btn` again; verify "Undo". Hover `#play-pause-btn` idle → "Start"; pause then resume; verify "Start" / "Pause" toggling. Tab-focus each button; verify the tooltip appears on focus (not only on hover). Verify the verbose `aria-label=` and `title=` strings ("Reset timer" / "Undo last session" / "Start or pause timer" / "Skip session") stay paired across state changes, while `data-tooltip=` carries the terse counterpart ("Reset" / "Undo" / "Start" / "Pause" / "Resume" / "Skip session") — both signals derive from the same engine state source so they update atomically; the verbose pair is preserved per CHK041 (WCAG 4.1.2).

**Acceptance Scenarios**:

1. **Given** `#stop-btn` in Focus mode, **When** the user hovers the button, **Then** a CSS-driven tooltip appears below it reading "Reset" within ≤ 150 ms (the tooltip CSS uses a short transition, not the native ~1 s delay).
2. **Given** `#stop-btn` after a focus completion (engine in Break or LongBreak mode), **When** the user hovers the button, **Then** the tooltip reads "Undo".
3. **Given** `#play-pause-btn` in idle (timer not running, not paused), **When** the user hovers, **Then** the tooltip reads "Start".
4. **Given** `#play-pause-btn` with the timer running, **When** the user hovers, **Then** the tooltip reads "Pause".
5. **Given** `#play-pause-btn` paused, **When** the user hovers, **Then** the tooltip reads "Resume".
6. **Given** `#skip-btn`, **When** the user hovers in any mode, **Then** the tooltip reads "Skip session" — no state variants, parity with the existing `aria-label=`.
7. **Given** any of the three control buttons, **When** the user keyboard-focuses it via Tab, **Then** the same tooltip appears (the CSS rule is `:hover, :focus-visible { ... }`, not `:hover` alone).
8. **Given** the rendered DOM for each control button, **When** a developer inspects the attribute set, **Then** `aria-label=` and `title=` hold the **same verbose** string for that button's state (e.g., "Reset timer" / "Undo last session" / "Start or pause timer" / "Skip session") and `data-tooltip=` holds the **terse** counterpart (e.g., "Reset" / "Undo" / "Start" / "Pause" / "Resume" / "Skip session"). Both signals derive from the same `engine.current_mode()` + run-state source, so flipping state updates the verbose pair and the terse tooltip atomically — but the verbose and terse strings are intentionally decoupled per CHK041 (verbose `aria-label` is the WCAG 4.1.2 accessible name; terse `data-tooltip` is the visible UI label).

### User Story 5 - Old visual baselines are regenerated only where the surface legitimately changed (cross-cutting, Priority: P3)

A PR reviewer opens the visual regression diff. Exactly the baselines that **must** legitimately differ — the Statistics view (now period-tabbed with Daily/Weekly/Monthly/Yearly sub-screens, each captured as a separate baseline), the new Daily view, and `tag-manager-chromium-linux.png` (which now shows 12 icon options: 3 remixicon + 9 Phosphor; the 5 emoji entries removed) — are regenerated. The control-button tooltips (Bundle D) don't regenerate a baseline because they're a hover/focus state not captured by the default screenshot. Baselines outside the touched surfaces (timer body itself, settings tabs, update notification) MUST NOT regenerate. The PR description carries one line of justification per regenerated baseline.

**Why this priority**: Integrity guarantee that the UI surface is honestly accounted for, not silenced. P3 because it's PR-time discipline, not runtime behaviour. Tied to **IV. Visual Regression Is The UI Contract** — explicit policy, not silent baseline updates.

**Independent Test**: Run the visual regression suite. Confirm failing baselines map exactly to the touched surfaces. Confirm no baselines for untouched screens (timer body, settings tabs, tag manager, update notification) flag a diff.

**Acceptance Scenarios**:

1. **Given** the PR ready for review, **When** the visual regression suite runs, **Then** the regenerated baselines are exactly: four per-period Statistics-view baselines `statistics-daily-chromium-linux.png`, `statistics-weekly-chromium-linux.png` (the cold-load default frame; supersedes the existing `calendar-chromium-linux.png` which is removed), `statistics-monthly-chromium-linux.png`, `statistics-yearly-chromium-linux.png`; one new view baseline `daily-chromium-linux.png` (the new Daily drill-down); and the timer view's `timer-chromium-linux.png` only if the tag-picker dropdown is open in the visual-regression scenario (today's frame does not open the dropdown, so this baseline likely does NOT regenerate). All four Statistics frames are required per CHK040 — no per-period frame may be elided.
2. **Given** each regenerated baseline, **When** the PR description is read, **Then** each carries a one-line note explaining the intended visual change (e.g., "`calendar-chromium-linux.png`: view renamed Statistics; old right-column mini-calendar + Today's Sessions moved to new Daily view; new period tabs at top with Weekly active").
3. **Given** any baseline outside the touched screens flagging a diff (`timer-chromium-linux.png` if the dropdown is closed, any `settings-*-chromium-linux.png`, `tag-manager-chromium-linux.png`, `update-notification-chromium-linux.png`), **When** the reviewer sees the failure, **Then** the diff is treated as a regression to fix in code — not absorbed by regenerating the baseline.
4. **Given** the sidebar visual surface (which now has four nav icons instead of three, plus the Calendar→`ph-chart-line-up` icon swap), **When** the visual-regression scenarios capture the timer / settings / etc. views, **Then** those baselines DO legitimately differ on the sidebar strip — either (a) sidebar capture is masked out of those baselines (preferred) so non-sidebar baselines stay locked; or (b) every cross-sidebar baseline regenerates and is justified per Acceptance Scenario 2. The PM brief's "timer body and settings tabs MUST NOT regenerate" is honoured by picking option (a).

### User Story 6 - PeakFocusTime line chart on the Weekly view (Bundle E, Priority: P3, cut-line)

A user on the Weekly statistics tab scrolls below the existing bar chart and tag-usage pie and sees a small SVG line chart titled **"Peak Focus Hour"**: 24 hourly x-axis points (00:00–23:00), y-axis is "average minutes focused per hour over the last 7 days", and the single peak hour is highlighted with a saturated dot + label (e.g., "10:00 — 42 min/day average"). It's a small read-only insight, not interactive.

**Why this priority**: P3 explicitly because this is **the cut-line**. If implementation timeline tightens, this is the first to defer to a follow-up issue without blocking the cycle. The other four bundles ship as a coherent visual surface; Bundle E is a leaf-node addition with no shared dependency. Tied to **II. Local-Only** (computed from the same `load_sessions` output the rest of the view reads).

**Independent Test**: With seeded sessions distributed across various hours of the last 7 days, navigate to Statistics → Weekly. Verify the Peak Focus Hour panel renders below the existing bar chart, the 24-point line accurately reflects per-hour averages, the peak-hour dot is positioned at the correct x-y, and the label reads the right "HH:00 — N min/day" string.

**Acceptance Scenarios**:

1. **Given** the Weekly tab with ≥ 7 days of session data, **When** the user scrolls to the bottom of the panel, **Then** the Peak Focus Hour line chart renders with 24 x-axis points and a single highlighted peak-hour dot.
2. **Given** the same Weekly tab with < 7 days of data (e.g., a fresh install with only today's sessions), **When** the chart renders, **Then** the y-values reflect the available days only (no division-by-zero / NaN) and a soft "Insufficient data — keep tracking to see your peak hour" label appears if fewer than 3 days are present.
3. **Given** Bundle E deferred to a follow-up, **When** the rest of the cycle ships, **Then** the Weekly tab renders without the Peak Focus Hour panel — Bundles A through D are not blocked.

### Edge Cases

- **Period swap with a non-existent cursor target**: User is on Daily at "May 12 2026", swaps to Yearly. The Yearly cursor anchors at the current year (2026), not "the year containing the Daily cursor". This is the deliberate decision in Acceptance Scenario 1.7 — cursor state does not transfer across period swaps. **[BEST-GUESS PM DECISION]** Anchored in the brief; not constitutionally weighted. Alternative (preserve cursor as "the period containing the previous cursor") was rejected because it confuses the user when they swap from Yearly to Daily and end up at "January 1 of the selected year" instead of today.
- **Daily view month grid + day-of-month clamping**: Selected day is May 31, user clicks `Next month →` to June; June 31 doesn't exist, so the cursor clamps to June 30. Pre-rework behaviour for `CalendarView`'s `on_next_month` uses `checked_add_months` which already handles this; the Daily view inherits the same helper.
- **Empty period bar chart**: Daily on a day with zero sessions renders 24 bars at the minimum-visible-height floor (≥ 4 px per bar — matches the existing 8 px floor at `src/src/components/calendar.rs:495-501`). No "Insufficient data" overlay on the bar chart itself; the tag-usage pie below shows an empty-state label.
- **Phosphor glyph rendering with the font not yet loaded**: First-render of a Phosphor icon before the webfont arrives shows an empty box (the `<i>` element has no content; the glyph comes from the font's pseudo-element via the `ph-cloud::before { content: "\xxxx" }` pattern). **[BEST-GUESS PM DECISION]** Acceptable on first render — vendoring the font via `copy-dir` means it loads from same-origin and is in the disk cache after the first navigation; the e2e test fixture preloads it before screenshots. Alternative (font-display: block to hide content until load) was rejected because the empty-box flash is < 100 ms and adding `block` would freeze the entire icon set on first paint, including unrelated remixicon glyphs.
- **Tag with `icon = ""` (empty string)**: A pre-rework tag with no icon (corrupt or hand-edited record) renders as an empty `<i>` element. Renderer dispatch returns "no icon" → no glyph; no fallback to brain. **[BEST-GUESS PM DECISION]** Empty-icon-as-no-icon matches the type-system encoding from Story 3 Acceptance 5; sentinel-fallback to a default icon would mask a data-integrity issue at the boundary.
- **Tooltip text drift between `aria-label`, `title`, `data-tooltip`**: Per CHK041, `aria-label=` and `title=` hold the **verbose** state string (`"Reset timer"` etc.); `data-tooltip=` holds the **terse** counterpart (`"Reset"` etc.). Both bind to derived Leptos signals sourced from the same `engine.current_mode()` + run-state computation, so state changes update verbose+terse atomically. A wasm-bindgen-test (FR-031) asserts (a) `aria-label == title` per button per state (the verbose pair stays paired) and (b) `data-tooltip` is the terse counterpart for the active state. The test MUST NOT assert `aria-label == data-tooltip` — that equality is intentionally **not** preserved.
- **Stop-button "Undo" tooltip semantics**: In Break/LongBreak mode, `#stop-btn` undoes the **last completed pomodoro** (decrements `completed_pomodoros` per `mod.rs:982-983` then resets). Per CHK041, the verbose `aria-label="Undo last session"` (current value at `mod.rs:1557`) is **preserved** for assistive tech; only `data-tooltip="Undo"` is the short form for the visible CSS tooltip. The earlier proposal of shortening `aria-label` to "Undo" was rejected as a regression in the screen-reader experience — decoupling the visible tooltip from the accessible name honours WCAG 4.1.2.
- **Statistics → Weekly cursor seeded from `BrowserClock`**: On cold load, the Weekly cursor anchors at the wall-clock now (matches `CalendarView`'s existing `BrowserClock.now_ms()` seed at `src/src/components/calendar.rs:318`). Host-side test builds resolve `BrowserClock` to the unix epoch; e2e runs use the real wall clock.
- **Removing the Statistics view's right-column mini-calendar (per Story 2 Acceptance 7)**: Existing e2e selectors `#prev-month`, `#next-month`, `#current-month`, `#calendar-grid` move to the Daily view; the off-viewport `#sessions-table-body` block (per CHK043 resolution) also moves to the Daily view. The visual-regression sidebar mask (Story 5 Acceptance 4) covers the move; the navigation e2e tests need updated assertions to look for those IDs in the Daily view, not the Statistics view. `tests/e2e/sessions-history.spec.js:31` migrates from `tapTab(page, "Calendar")` to `tapTab(page, "Daily")` in the same PR. Selector strings unchanged; only the host container changes.
- **Phosphor font asset size**: The Phosphor webfont is ~250 KB across all weights; we ship only the **regular** weight to keep the bundle lean. **[BEST-GUESS PM DECISION]** All 9 picker icons render fine in regular; thin/bold are not used.
- **Pipboy theme's sidebar `border-right` is intentional**: `src/style/themes/pipboy.css:428,437,446` has three `border-right: 1px solid var(--*-color)` rules on `.sidebar.focus`, `.sidebar.break`, `.sidebar.longBreak`. These are the only theme where the sidebar→main edge is a hard 1-px border rather than the box-shadow glow — this is deliberate retro-CRT-terminal aesthetic for the pipboy theme and predates this feature. SC-015 explicitly grandfathers these three hits; FR-036's "no `border-right`" constraint applies to **new** rules only. Default, light, and dark themes preserve the box-shadow glow at `sidebar.css:18-35`.

- **`Period` (UI-side enum, new)**: Closed sum type `Period::{Daily, Weekly, Monthly, Yearly}`. Held in the Statistics view as `RwSignal<Period>` seeded to `Period::Weekly`. Drives the bar-chart's parameters, the navigator's labels, and the tag-usage scope. Not persisted; not serialised across the Tauri bridge.
- **`BarChartProps` (UI-side component param, new)**: `{ max_scale: u32, x_axis_labels: Vec<String>, bar_values: Vec<u32>, min_bar_height_px: u32 }`. The single reusable BarChart's input contract. Daily / Weekly / Monthly / Yearly each construct one and render `<BarChart {...}/>`.
- **Statistics period cursor (UI-side, new)**: A per-period `DateTime<Utc>` — one cursor for Daily (anchored on a day), one for Weekly (Monday), one for Monthly (first of month), one for Yearly (first of year). Held in four signals or a single `enum Cursor { Daily(DateTime), Weekly(DateTime), Monthly(DateTime), Yearly(DateTime) }`. Resets to "current" on period swap per FR-008.
- **Daily view state (UI-side, new)**: `(month_cursor: RwSignal<DateTime<Utc>>, selected_day: RwSignal<DateTime<Utc>>)`. Both seed from `BrowserClock.now_ms()`. Day-clamp logic on month roll matches `CalendarView::on_next_month`.
- **`IconClass` (UI-side enum, new)**: Closed sum type `IconClass::{Remix(&str), Phosphor(&str), Glyph(&str)}` used by the tag-renderer's typed-prefix dispatch (FR-023). The constructor parses an icon-name string at the boundary; downstream rendering branches exhaustively on the enum.
- **Tooltip-text signals (UI-side, new)**: Two `Signal<String>`s per control button (`verbose_label` and `terse_tooltip`), both derived from `engine.current_mode()` + run-state predicates. `verbose_label` binds to `aria-label=` and `title=`; `terse_tooltip` binds to `data-tooltip=`. Per CHK041, the verbose and terse strings are intentionally decoupled — both update atomically on state change because they share the same upstream derivation, but their string contents differ (e.g., `aria-label="Reset timer"` vs `data-tooltip="Reset"`).

## Assumptions

- **A1 — UI-only rework, engine and bridge untouched**: Per FR-040 and FR-045. The timer engine, manager state machines, persistence helpers, and Tauri command set are out of scope. This anchors the feature against Principle I (The Timer Is Sacred) and Principle VI (The Tauri Boundary Is Stable) — both stay untouched. **Test-first (Principle V) does NOT apply** because there is no stateful-engine change; new state is local to view components and is covered by e2e + wasm-bindgen-test. **Exception**: the day-clamp helper covered by SC-008 (`checked_add_months` end-of-month clamping) is pure time-keeping math. If implemented as a standalone function (rather than inlined into a Leptos signal handler), the test-first commit ordering of Principle V applies to it — RED commit precedes the GREEN implementation.
- **A2 — Period state is session-local UI state, not persisted**: **[BEST-GUESS PM DECISION]** Per FR-002 and the brief. Refreshing the view returns to Weekly + current week, matching today's pre-rework cold-start behaviour. Alternative (persist last-used period in `Settings`) was rejected because (a) it's UI-only state with no cross-platform expectation, (b) avoiding the `Settings` evolution keeps the Tauri bridge clean per Principle VI, and (c) the user can re-select with a single click.
- **A3 — BarChart axis policy**: **[BEST-GUESS PM DECISION]** Daily uses a fixed 60 min/hour ceiling (a focus session can't physically exceed 60 minutes of one hour); Weekly/Monthly/Yearly use dynamic-max with floors (Weekly ≥ 20, Monthly ≥ 50, Yearly ≥ 100). Floors match the natural scale of the period — at small data volumes the dynamic max would make a single 5-min session look like a full bar. Numbers from the PM brief; not constitutionally anchored. **Rounding policy** (for readable tick labels): Weekly and Monthly round `observed_max` up to the nearest 10 before applying the floor (e.g., 87 → 90, 91 → 100); Yearly rounds up to the nearest 50 (e.g., 91 → 100, 151 → 200). Rounding prevents awkward Y-axis tick labels like `22.5, 45, 67.5`. Daily has no rounding (fixed 60 ceiling). See `BarChartProps` in `data-model.md` for the exact formula.
- **A4 — Cursor does NOT transfer across period swaps**: **[BEST-GUESS PM DECISION]** Per FR-008 and Acceptance Scenario 1.7. Alternative (preserve the cursor's containing period as the new cursor anchor) was rejected because user-test intuition is that "switching from Yearly to Daily" means "go to today", not "go to Jan 1 of the year I was viewing".
- **A5 — Statistics view loses the right-column mini-calendar; Daily view inherits it**: Per FR-019. The right-column duplication is the rework's primary cleanup — the existing `CalendarView` was a single weekly summary + mini-month-grid + sessions-panel mashup; period tabs and the Daily drill-down split it into two coherent views.
- **A6 — New Daily nav icon is Phosphor, swapped Statistics nav icon is Phosphor**: **[BEST-GUESS PM DECISION]** Daily = `ph-calendar-check`; Statistics (formerly Calendar) = `ph-chart-line-up`. Sets the Phosphor font as the canonical sidebar-icon source going forward without breaking the existing `ri-timer-line` and `ri-settings-3-line` selectors. Alternative (keep both as remixicon) was rejected because remixicon doesn't have a clean "chart-line" + "drill-down day" pair and Phosphor is already shipping for tag icons anyway.
- **A7 — Phosphor font is vendored locally, not from CDN**: Per FR-022 and the Clarifications-resolved log. The e2e suite's `_blockExternal` fixture blocks CDN fetches; the existing remixicon vendor pattern at `src/index.html:19-27` is the precedent. **Verified-fact correction over the PM brief**: the brief said "CDN link in `index.html`", which would break the e2e visual-regression suite.
- **A8 — Phosphor regular weight only**: **[BEST-GUESS PM DECISION]** Per the Edge Cases entry "Phosphor font asset size". All 9 picker icons render correctly in regular; bold/duotone/thin are unused. ~50 KB regular vs ~250 KB all-weights.
