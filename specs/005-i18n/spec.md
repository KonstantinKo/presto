# Feature Specification: Multi-Locale UI With In-App Language Switcher

**Feature Branch**: `005-i18n`
**Created**: 2026-05-13
**Status**: Draft
**Input**: User description: "Internationalization (i18n) for the presto desktop app. Four locales — English (EN, default + source of truth), German (DE), Italian (IT), Turkish (TR) — all visible UI strings extracted into a compile-time message catalogue, with a Language dropdown in Settings → General. Locale switching takes effect immediately (no restart). Locale resolution at startup is persisted-locale → OS-locale-mapped-to-supported → English fallback. Library pick is deferred to plan/research.md; the spec mandates a compile-time-checked typed key API (no stringly-typed `t(\"key\")` calls). Catalogues bundled at compile time — no network fetch. No new Tauri commands expected. Visual regression budget: only `settings-general-chromium-linux.png` regenerates."

## Clarifications resolved

- 2026-05-13: The locale dropdown's option labels are the **native self-names** of each locale (`English`, `Deutsch`, `Italiano`, `Türkçe`) regardless of the active UI locale. The dropdown's surrounding label ("Language" / "Sprache" / "Lingua" / "Dil") IS localised. Rationale: a user who accidentally lands in a locale they don't read still needs to recognise their own language in the picker; a non-localised option list is the universal escape hatch.
- 2026-05-13: Locale switching takes effect immediately on selection — no app restart, no toast that demands a reload, no transient mixed-locale state. All visible strings rebind via the shared reactive locale signal in the same render tick the dropdown's change handler fires.
- 2026-05-13: The English baselines remain the visual-regression source of truth. Per-locale baseline captures are **out of scope** here — adding three more screenshot sets per touched screen would quadruple the baseline count and the English source-of-truth is the contract anchor. Only `settings-general-chromium-linux.png` regenerates (the new Language dropdown becomes visible). Other baselines are captured in English and stay locked.
- 2026-05-13: The locale enum's wire shape is **lowercase** (`"en"`, `"de"`, `"it"`, `"tr"`) via `#[serde(rename_all = "lowercase")]`. This matches the existing `theme` field's lowercase string convention at `crates/presto-ipc/src/settings.rs:135-141` (`"auto"` / `"light"` / `"dark"`) rather than the kebab-case convention used by `AmbientSoundType` and `StatusBarDisplay`. Two-letter ISO-639-1 codes have no word boundary; lowercase suffices.
- 2026-05-13: Date/time formatting is **not** localised in v1. `chrono`-rendered timestamps (statistics axis labels, daily-view date headers, calendar dates) stay in their existing English formatting. UI-string-side strings around them (e.g. "Today's Sessions", month names) ARE localised. Deferring per-locale date formatting keeps the surface tractable; revisit in a follow-up if user feedback objects.
- 2026-05-13: Pluralization rules beyond the picked library's built-in support are **out of scope**. Where English uses pluralization-sensitive phrasing ("1 session" vs "5 sessions"), the catalogue carries whatever pluralization affordance the library provides; nothing more elaborate is built on top.

## User Scenarios & Testing *(mandatory)*

> This feature is **one user-facing capability** (in-app locale switching across the entire visible UI surface) with one underlying integrity guarantee (legacy settings-file compatibility), one optional OS-locale convenience, and one cross-cutting PR-time discipline (visual-regression budget). Constitutional anchors are cited inline by name **and** number, mirroring the spec 002 / 003 / 004 precedent.

### User Story 1 - Switching the UI language from English to a non-default locale (Priority: P1)

A user opens Settings → General, sees a new **Language** control row above the timer-durations section, and picks **Deutsch** from a dropdown showing four native self-names (`English`, `Deutsch`, `Italiano`, `Türkçe`). Immediately — no restart, no reload toast — every visible string the app renders flips to German: the sidebar nav tooltips, the timer mode badges (`Focus` → `Fokus`, `Break` → `Pause`, `Long Break` → `Lange Pause`), the timer state suffixes (`Paused` → `Pausiert`, `Auto-paused` → `Auto-pausiert`, `Overtime` → `Überzeit`), the control button labels and their verbose `aria-label`s, the Settings tab names and every setting's label + helper text + toast strings, the statistics view's period tabs and tile labels and "No data" empty states, the daily view's header ("Daily Overview" → "Tagesübersicht") and "No sessions completed" text, the update notification's strings, the tag picker's "New tag…" placeholder and "Choose tag" header, and the calendar's month names and day-of-week headers. They navigate the whole app; every visible string is German. They reopen Settings and the surrounding label has changed to `Sprache` while the dropdown options still read `English / Deutsch / Italiano / Türkçe` (option labels stay native self-names, not double-translated).

**Why this priority**: This is the entire user-facing value of the feature. Without it, the feature is invisible. Tied to **III. Type Safety Over Defensive Code** (the message catalogue is dispatched through a compile-time-checked typed-key API generated by the picked library's proc-macro; stringly-typed `t("some.key")` calls where the compiler doesn't verify the key exists are rejected — a key typo or a missing translation must fail at compile time, not at render time with a `[MISSING: some.key]` fallback) and **II. Local-Only** (the message catalogues for all four locales are bundled at compile time into the WASM binary; no runtime network fetch, no CDN-loaded JSON, no on-disk locale file outside the app bundle).

**Independent Test**: Cold-start the app with `appearance.locale = "en"` (default). Verify every visible string in every view (timer, sidebar, settings, statistics, daily, tags, calendar, update notification) renders in English. Switch to `de` via the Settings → General dropdown. Without a restart, verify every visible string in every view renders in German, the surrounding `Language` label has become `Sprache`, and the dropdown options still read native self-names. Repeat with `it` (expect `Lingua`) and `tr` (expect `Dil`). Switch back to `en` and confirm the original English strings are restored.

**Acceptance Scenarios**:

1. **Given** Settings → General, **When** the user looks at the controls above the timer-durations section, **Then** a new "Language" row is visible carrying a single-line label (localised to the active locale) and a dropdown (`#locale-selector`) whose four options are `English`, `Deutsch`, `Italiano`, `Türkçe` in that order, with the option matching the active locale pre-selected.
2. **Given** the active locale is English, **When** the user picks `Deutsch` from the Language dropdown, **Then** within the same render tick (no perceptible delay, no transient mixed-locale frame) every currently-mounted visible string re-renders in German — sidebar tooltips, timer screen, settings page itself, calendar (if visible), statistics tiles, daily view, update notification, tag picker.
3. **Given** the active locale is German, **When** the user navigates to a previously-unmounted view (e.g. Statistics if they were on the timer), **Then** that view renders in German on first paint — no English flash, no remount-after-language-detect race.
4. **Given** the locale is set to any non-English value, **When** the user opens Settings → General, **Then** the surrounding Language label reads `Sprache` (de) / `Lingua` (it) / `Dil` (tr) and the four dropdown option labels still read `English`, `Deutsch`, `Italiano`, `Türkçe` (native self-names, never re-translated).
5. **Given** the locale is `tr`, **When** the timer screen renders mode badges and control buttons, **Then** the strings render in Turkish (e.g. `Focus` → `Odaklan`, `Break` → `Mola`, `Reset` → `Sıfırla`, `Skip session` → `Oturumu atla`) AND the corresponding verbose `aria-label` attributes are also Turkish (e.g. `aria-label="Reset the timer to the start of the focus session"` → its Turkish equivalent), not the English originals.
6. **Given** the locale is `it`, **When** the calendar renders, **Then** month names (`January` → `Gennaio`, …, `December` → `Dicembre`) and day-of-week headers (`Sun`, `Mon`, …, `Sat` → `Dom`, `Lun`, …, `Sab`) are Italian. The numeric date components rendered by `chrono` remain in their existing format (per Clarifications resolved 2026-05-13 — date *formatting* is out of scope; surrounding *strings* are in scope).
7. **Given** the user just switched from English to a non-English locale, **When** they trigger an auto-save toast (e.g. by editing focus duration), **Then** the toast strings — both the success path (`"Settings saved"`) and the failure path (`"Failed to save settings"`) — render in the active locale.

### User Story 2 - Legacy settings load unchanged after the locale field is added (Priority: P1)

A user with a pre-005 `settings.json` opens the new build. The file deserialises cleanly — no migration prompt, no error state, no data loss. `appearance.locale` defaults to `Locale::En` (English). The user sees the app in English on first launch, exactly as before, until they explicitly pick a different locale from the Settings → General dropdown.

**Why this priority**: Underlying integrity guarantee that makes Story 1 safe to ship — evolving `AppearanceSettings` would otherwise be a data-loss / first-launch-error hazard. Tied to **VI. The Tauri Boundary Is Stable** (the new `locale` field carries `Option<Locale>` with `#[serde(default)]` → `None` so older on-disk records deserialise; pattern mirrors feature 002's metronome and feature 004's `ambient_sound_*` evolutions on `NotificationSettings`) and **III. Type Safety Over Defensive Code** (the closed `Locale` enum's lowercase wire shape `"en" | "de" | "it" | "tr"` is the type-system encoding of the supported set; an out-of-set value on the wire fails serde deserialisation and falls back to `None` via the `#[serde(default)]` value rather than rendering with a broken locale). The `Option<Locale>` discriminant (`None` vs `Some(_)`) is the authoritative "explicit vs. default" signal; value-equality against `Locale::En` MUST NOT be used as a proxy (FR-009).

**Independent Test**: Seed `settings.json` whose `appearance` block lacks the `locale` key entirely. Open the new build. The settings deserialise successfully (`locale` → `None`); the active locale resolves to English (via OS detection or fallback); the Settings → General Language dropdown shows `English` pre-selected. No first-run prompt, no error toast, no settings-tab error state. Save settings (e.g. by toggling any unrelated field) and reload — the on-disk `appearance.locale` is now `"en"` (i.e. `Some(Locale::En)` serialised), and subsequent cold starts use the persisted value directly without re-running OS detection.

**Acceptance Scenarios**:

1. **Given** a pre-005 `settings.json` whose `appearance` block lacks the `locale` key, **When** the new build reads the file, **Then** the field deserialises to `None` (no explicit locale — the resolver will consult OS detection).
2. **Given** a new-build `appearance` record persisted with an explicit `Some(Locale::En)`, **When** it is re-serialised to disk and re-read, **Then** the round-trip preserves the value byte-stable and the on-disk JSON encodes `locale` as the lowercase string `"en"` — and this `Some(Locale::En)` is distinct from `None` (OS detection is NOT re-run on subsequent cold starts).
3. **Given** a new-build `appearance` record persisted with each non-default locale (`Locale::De`, `Locale::It`, `Locale::Tr`), **When** it is re-serialised and re-read, **Then** each round-trips byte-stable and encodes on the wire as `"de"` / `"it"` / `"tr"` respectively.
4. **Given** a hand-edited `settings.json` whose `appearance.locale` field carries an unsupported value (e.g. `"fr"`, `"zh-CN"`, `null`, `""`, `42`), **When** the new build reads the file, **Then** the field falls back to the `#[serde(default)]` value of `None` — the resolver treats this as "no explicit locale" and runs OS detection, ultimately landing in English if the OS locale is also unsupported. No panic, no error toast.
5. **Given** a pre-005 `settings.json` already containing the existing `theme` and `timer_theme` fields (from prior features), **When** the new build reads it and writes it back, **Then** both existing fields are preserved byte-stable — the new feature's serde-evolution does not corrupt the prior fields.
6. **Given** the existing `AppearanceSettings::default()` impl, **When** it is invoked from any code path that previously returned the default (cold start with no settings file, error fallback paths), **Then** the returned `locale` field is `None` — the resolver runs OS detection (or falls back to English), matching pre-005 cold-start behaviour (the user sees English by default unless their OS locale is a supported non-English locale).

**Why this priority**: Integrity guarantee that the UI surface is honestly accounted for, not silenced. P2 because it is PR-time discipline, not runtime behaviour. Tied to **IV. Visual Regression Is The UI Contract** — baselines are the UI contract, and changes carry per-baseline justification notes. Mirrors feature 002 Story 6, feature 003 CHK040, and feature 004 Story 3's posture.

**Independent Test**: Run the visual regression suite. Confirm the failing baseline maps exactly to `settings-general-chromium-linux.png` (the Settings → General tab). Confirm no baselines for untouched screens (timer, settings notifications, settings shortcuts, settings theme, settings automation, settings goals, settings advanced, settings updates, statistics × 4 periods, daily, tag-manager, update-notification) flag a diff.

**Acceptance Scenarios**:

1. **Given** the feature's PR ready for review, **When** the visual regression suite runs with `appearance.locale` set to `"en"` (the source-of-truth locale for baselines), **Then** the only baseline that flags a diff is `settings-general-chromium-linux.png`.
2. **Given** the regenerated baseline, **When** the PR description is read, **Then** the baseline has a one-line note explaining the intended visual change. No bare PNG diff lands without prose.
3. **Given** any baseline outside Settings → General flagging a diff, **When** the reviewer sees the failure, **Then** the diff is treated as a regression (fix the code) — not absorbed by regenerating the baseline. The visible chrome of the non-Settings-General screens MUST NOT shift as a side effect of the i18n string extraction (a typical drift mode: extracting a string changes its width and reflows the layout; per FR-021 this is a code regression, not a re-baseline).

### User Story 4 - OS-locale detection on first launch (Priority: P3, optional convenience)

A user installs the app for the first time on a machine whose OS locale is German (`navigator.language` returns `"de-DE"` or similar). On cold start, the app detects the OS locale, maps it to the nearest supported locale (`de-DE` → `de`), and renders the entire UI in German on first paint — the user never has to open Settings to switch. If the OS locale maps to an unsupported language (e.g. `"fr-FR"`, `"zh-CN"`, `"ja-JP"`), the app falls back to English.

**Why this priority**: Nice-to-have convenience that reduces first-launch friction for non-English users; not on the critical path because the explicit Settings → General dropdown (Story 1) is the universal fallback. P3 because implementation complexity is non-trivial (needs to gate on "first launch ever" vs "user already saved settings"), and shipping without OS detection still delivers Story 1's full value with a one-time manual locale pick. Tied to **II. Local-Only** (`navigator.language` is a Web platform API; no network, no telemetry) and **VI. The Tauri Boundary Is Stable** (detection happens entirely in the Leptos frontend via `web_sys::window().navigator().language()`; no new Tauri command required).

**Independent Test**: With no prior `settings.json` (simulating a fresh install), launch the app under a host where `navigator.language` returns `"de-DE"`. Verify the UI renders in German on first paint. Launch again under `"tr"` (bare two-letter code) — UI renders in Turkish. Launch under `"it-CH"` (Italian, Switzerland) — UI renders in Italian. Launch under `"fr-FR"` (unsupported) — UI renders in English. Launch under `"de"` after a `settings.json` already exists with `locale = "it"` — UI renders in Italian (persisted setting wins over OS detection).

**Acceptance Scenarios**:

1. **Given** no `settings.json` exists yet (fresh install or settings reset), **When** the app cold-starts and `navigator.language` returns a string whose two-letter prefix matches one of the four supported locales (`en-US`, `de-DE`, `de-AT`, `de`, `it-IT`, `it-CH`, `tr-TR`, `tr`), **Then** the detected locale is applied for the cold-start render and persisted on the first save.
2. **Given** the same fresh-install precondition, **When** `navigator.language` returns a string whose two-letter prefix does NOT match a supported locale (e.g. `fr-FR`, `zh-CN`, `ja-JP`, `pt-BR`, `es-ES`), **Then** the app falls back to English on cold start.
3. **Given** a `settings.json` already exists with `appearance.locale` set to `Some(supported_value)` (any of the four variants, including `Some(Locale::En)`), **When** the app cold-starts under any OS locale, **Then** the persisted `Some(_)` value takes precedence over the detected OS locale — OS detection runs ONLY when the persisted value is `None` (the `#[serde(default)]` path, meaning no locale was ever explicitly saved).
4. **Given** the OS-detected locale is applied on first paint, **When** the user explicitly picks a different locale from the Settings → General dropdown, **Then** the explicit pick wins and persists; OS detection is not re-consulted on subsequent launches.
5. **Given** the host has no `window.navigator.language` available (an exotic dev-server / e2e-mock context), **When** the app cold-starts, **Then** the detection short-circuits to English without panicking — the bridge-availability discipline from Principle VI extends to web platform API availability.

### Edge Cases

- **Mixed-locale frame during switch**: Locale switching MUST NOT produce a transient frame where some strings have flipped to the new locale and others are still in the old one. The locale is held in a single shared reactive signal (Leptos `RwSignal<Locale>`); every translation-consuming view re-derives from it; the reactive system batches the re-renders into a single tick. **[BEST-GUESS PM DECISION]** No explicit "translation barrier" mechanism beyond Leptos signal semantics is required — the framework's batching is sufficient.
- **String width drift across locales**: Some target strings will be wider or narrower than their English originals (German is typically ~30% longer; Turkish has long agglutinative compounds; Italian has occasional very long words). Layout MUST tolerate this — controls do not overflow, do not clip, do not push other controls off-screen. **[BEST-GUESS PM DECISION]** No layout tweaks are made specifically for non-English locales beyond fixing genuine overflow regressions surfaced by the visual-regression-against-English contract; Principle IV is honoured by the English-baseline anchor. If a non-English string causes the English baseline to drift (because the container's intrinsic size leaks the longest string), that is a regression to fix in code (FR-021 / Story 3 AC 3).
- **`aria-label` strings translated independently of visible text**: The verbose `aria-label` strings on control buttons (e.g. "Reset the timer to the start of the focus session") are distinct catalogue entries from the visible button text ("Reset"). Both are localised. Per Principle III, both keys are compile-time-checked.
- **Untranslated string at render time**: With a typed-key API enforced at compile time (FR-005), a key the picked library knows about but a specific locale doesn't have a translation for is a build-time error in CI — not a runtime fallback. (Most candidate Leptos i18n libraries treat missing-translation as a compile-time or build-time check via their proc-macro.) **[BEST-GUESS PM DECISION]** If the picked library treats missing-translation as a runtime fallback to the source locale instead, the spec mandates the library is configured to upgrade that to a hard build-time error (FR-006).
- **Catalogue file format and on-disk layout**: The exact catalogue file format (JSON / TOML / YAML / Fluent FTL / inline Rust macro arms) and on-disk layout (one file per locale vs one file per language with per-key locale columns) is a **library-dependent plan decision**. The spec specifies the contract (compile-time-checked, no runtime fetch, bundled into the WASM binary); the plan/research.md picks the library and the file format follows from that pick.
- **Pluralization for "1 session" vs "5 sessions"**: Where English uses count-sensitive phrasing, the catalogue uses whatever pluralization affordance the picked library provides for free (most Leptos i18n libraries support ICU MessageFormat-style `{count, plural, ...}` or Fluent's `select` blocks). Building bespoke pluralization logic on top is out of scope. **[BEST-GUESS PM DECISION]** If the picked library has no pluralization support at all, individual English strings that depend on count are rewritten to avoid the pluralization-sensitive phrasing (e.g. `"Sessions: 5"` instead of `"5 sessions"` / `"1 session"`).
- **Date/time strings rendered by `chrono`**: Per the 2026-05-13 clarification, `chrono`-formatted timestamps stay English in v1. Surrounding labels (month names in calendar headers, "Today's Sessions" header on daily view, "Daily / Weekly / Monthly / Yearly" period tabs on statistics) ARE localised. A user in DE may see `"Wöchentlich"` (period tab) above `Mon, May 13` (chrono timestamp) in the same view; this is acceptable for v1 and is surfaced as A8.
- **Locale name in About / version dialog**: **[BEST-GUESS PM DECISION]** The About / update-notification surface is in scope (per the brief's UI surface list — update notification strings); the locale code itself is not displayed to the user anywhere except as the dropdown option labels (and even there as native self-names, not as codes). The on-disk wire string `"en"` / `"de"` / `"it"` / `"tr"` is an implementation detail.
- **Locale change while a focus session is running**: Locale is purely UI-side. A locale change MUST NOT pause the timer, modify engine state, emit a session event, or otherwise touch the deterministic state machine (Principle I). The timer screen's mode badge re-renders in the new locale at the next render tick; the session's `time_remaining_secs` and `current_mode` are bit-for-bit unchanged.
- **Locale change does not invalidate cached translations**: The picked library MUST be configured so that switching between the four supported locales is a constant-time signal flip with no async loading step — every locale's catalogue is already resident in memory after WASM init. (FR-007.)
- **Calendar with `weekStartsOn` ≠ Sunday under non-English locales**: **[BEST-GUESS PM DECISION]** Out of scope. The calendar's week-start day MAY differ by locale in a future feature; v1 keeps the existing week-start convention regardless of locale. Day-of-week headers ARE translated per-locale (e.g. `So Mo Di Mi Do Fr Sa` for German), but the column order remains Sunday-first across all locales — this is a deliberate v1 limitation per the out-of-scope week-start carve-out. DE/IT/TR users will see translated headers in non-cultural-norm column order; per-locale week-start ships as a follow-up issue post-merge. **PM action required at end-gate: file a `wontfix` follow-up issue for Monday-first week-start for DE/IT/TR locales.**
- **Beta-coverage indicator**: If translation coverage at ship time is <100% for a given non-English locale (i.e. some keys still rely on the source-locale fallback baked into the picked library), the Settings → General dropdown MAY render a subscript `(beta)` next to that locale's native self-name. **[BEST-GUESS PM DECISION]** This is a P3 nice-to-have surfaced as User Story 5 below; if all four locales reach 100% coverage at ship time the indicator is omitted entirely.

### User Story 5 - Translation-coverage indicator on incomplete locales (Priority: P3, optional)

If, at ship time, a non-English locale has incomplete translation coverage (some keys still fall back to the source locale), the Settings → General dropdown shows a small `(beta)` badge next to that locale's native self-name (e.g. `Türkçe (beta)`). The badge is omitted if the locale is 100% covered. The badge has no functional effect — picking a `(beta)` locale still switches the UI to that locale; untranslated strings simply render in English (the source-locale fallback).

**Why this priority**: Sets user expectation honestly when shipping with partial translation coverage; not on the critical path because if all four locales are 100% covered the badge is unneeded. P3 because it is purely informational. Tied to **III. Type Safety Over Defensive Code** indirectly — the coverage check is built on the typed-key catalogue (compile-time-known set of keys per locale), so the badge logic is itself type-safe rather than running on a stringly-typed map.

**Independent Test**: Build the app with one or more deliberately-incomplete locales (e.g. Turkish missing 5% of keys). Open Settings → General. Verify the dropdown shows `Türkçe (beta)` for Turkish and the other locales without the badge. Pick `Türkçe (beta)` — the UI switches to Turkish; the untranslated 5% of keys render in English. Build the app again with Turkish brought to 100%. The badge disappears.

**Acceptance Scenarios**:

1. **Given** a non-English locale's catalogue is missing one or more keys (relative to the English source-of-truth set), **When** the Settings → General dropdown renders, **Then** that locale's option is suffixed with a `(beta)` badge that visually distinguishes it from fully-covered options.
2. **Given** every non-English locale is 100% covered, **When** the dropdown renders, **Then** no `(beta)` badges appear on any option.
3. **Given** the user picks a `(beta)`-flagged locale, **When** the UI switches, **Then** keys present in that locale's catalogue render in that locale; keys missing from it render in English (the source-locale fallback baked into the picked library). The mixed-language rendering is acceptable for a `(beta)` locale and is part of the badge's contract.

## Requirements *(mandatory)*

### Functional Requirements

#### Behaviour — settings shape and defaults (constitutional anchors III, VI)

- **FR-001**: `AppearanceSettings` (in `crates/presto-ipc/src/settings.rs`) MUST gain one new field `locale: Option<Locale>` carrying `#[serde(default)]` so pre-005 `settings.json` records (lacking the `locale` key) deserialise to `None` (no explicit locale set). `None` means "user has never explicitly chosen a locale" — the resolver then consults the OS-detected locale. A user who explicitly picks any locale (including English) writes `Some(Locale::En)` / `Some(Locale::De)` / etc., and subsequent cold starts use the persisted value verbatim without re-running OS detection. This distinguishes "explicit English" from "default English" and fixes the German-user-picks-English regression (Fix A).
- **FR-002**: `Locale` MUST be a closed sum-type Rust enum with exactly four variants — `En`, `De`, `It`, `Tr` — defined alongside `AppearanceSettings` in `crates/presto-ipc/src/settings.rs` (or a sibling module within the same crate). Its wire shape MUST be `lowercase` (via `#[serde(rename_all = "lowercase")]`), producing on-disk strings `"en"`, `"de"`, `"it"`, `"tr"`. This matches the existing lowercase string convention for the `theme` field (`"auto"` / `"light"` / `"dark"`) rather than the kebab-case convention used by `AmbientSoundType` and `StatusBarDisplay` — two-letter ISO-639-1 codes have no internal word boundary, so kebab-case is unnecessary.
- **FR-003**: Default value MUST be `Locale::En`. The `Default` impl on `Locale` MUST return `En`. The cold-start defaults from `AppearanceSettings::default()` MUST stay bit-for-bit compatible with pre-005 cold-start behaviour — a fresh install with no `settings.json` and no OS-detection (e.g. `navigator.language` unavailable) renders the UI in English.
- **FR-004**: An out-of-set wire value (e.g. `"fr"`, `null`, `""`, `42`, a typo like `"english"`) MUST NOT deserialise as a valid `Locale`. Per Principle III, serde's strict enum deserialisation rejects the value and the `#[serde(default)]` attribute returns `Locale::En`. No silent best-effort coercion, no runtime "did you mean" branching.

#### Behaviour — catalogue dispatch and typed key API (constitutional anchors II, III)

- **FR-005**: Every visible UI string in the scope listed under FR-013 MUST be dispatched through a **compile-time-checked typed-key API** generated by the picked Leptos i18n library's proc-macro. Stringly-typed lookups (`t("some.key")` where the compiler does not verify the key exists) are forbidden. A key typo MUST fail the build, not the render. Library-pick selection is deferred to plan/research.md; candidates documented there at minimum include `leptos-fluent`, `leptos-i18n`, `leptos_i18n_macro`, and `leptos-router-i18n`. The spec specifies the typed-key contract; the plan picks the library that satisfies it.
- **FR-006**: A key present in the source-of-truth (English) catalogue but missing from a target locale's catalogue MUST be a build-time / CI-time error, not a render-time silent fallback to a `[MISSING: ...]` placeholder or a hard crash. The picked library MUST be configured to upgrade missing-translation to a hard failure during the production build. Source-locale fallback at render time is permitted only for User Story 5's optional `(beta)` coverage indicator path, and only when the library cannot be statically configured to reject the gap. **CI enforcement**: if the picked library's proc-macro fails `cargo build --frozen` on missing keys (preferred), no extra CI step is needed. If the library treats missing-translation as a runtime fallback, the plan MUST add a dedicated CI lint step (e.g. `check-translation-completeness.sh` registered in `.agentex.yml`'s `lint:` block) that fails CI when any key in the English catalogue is absent from any of the three target catalogues. The plan documents which path the picked library requires.
- **FR-007**: Switching between the four supported locales at runtime MUST be a constant-time reactive-signal flip — no async loading step, no network fetch, no decode-on-demand. All four locales' catalogues MUST be resident in WASM memory after init. (Principle II — local-only; no CDN, no late-loaded JSON.)
- **FR-008**: Message catalogues MUST be bundled at compile time into the WASM binary (e.g. via the picked library's `include_str!`-style macro or its proc-macro's compile-time-embedded artefacts). No catalogue MAY be fetched from a network URL, loaded from a path outside the bundle, or downloaded as part of the auto-updater payload beyond what the WASM binary itself carries.

#### Behaviour — locale resolution at startup (constitutional anchors II, III)

- **FR-009**: At cold start, the active locale MUST be resolved in this strict order: (1) the persisted `appearance.locale` value from `settings.json` if `Some(_)` (any explicitly-saved value, including `Some(Locale::En)`) — this value is used verbatim, OS detection is NOT run; (2) if the persisted value is `None` (i.e. the `#[serde(default)]` path produced `None`, meaning no locale has ever been explicitly saved), the OS-detected locale via `web_sys::window().navigator().language()` mapped by its two-letter prefix to the nearest supported variant (`de-AT`, `de-CH`, `de` → `De`; `tr-TR`, `tr` → `Tr`; etc.); (3) if neither path yields a supported locale, fall back to `Locale::En`. The `Option<Locale>` discriminant is the authoritative "explicit vs. default" signal — value-equality against `Locale::En` MUST NOT be used as this proxy.
- **FR-010**: The OS-detection step (FR-009 step 2) MUST be tolerant of `navigator.language` being unavailable or returning an unexpected value (empty string, `null`, an unparseable string). In all degenerate cases the detection short-circuits to English without panicking.
- **FR-011**: Once a user has explicitly saved a locale via the Settings → General dropdown, subsequent cold starts MUST consult only the persisted `Some(Locale)` value — OS detection is NOT re-run. The `Option<Locale>` discriminant is authoritative: `Some(_)` (any variant, including `Some(Locale::En)`) means "user has explicitly chosen; do not re-detect". `None` means "no explicit choice yet; OS detection may run". On first save after upgrade (legacy settings lacking the `locale` key), the resolver writes `Some(resolved_locale)` to disk, so subsequent launches short-circuit to `Some(_)` and skip OS detection (legacy migration path).
- **FR-012**: The active locale MUST be exposed to view code as a single shared reactive signal (a Leptos `RwSignal<Locale>` or equivalent), seeded at app boot from the resolved cold-start locale and updated in place whenever the Settings → General dropdown's change handler fires. Every translation-consuming view MUST read from this signal so the framework's reactive batching produces a single-tick re-render on locale change (Edge Case: mixed-locale frame avoidance).

#### Behaviour — UI scope of strings to be localised (constitutional anchor III)

- **FR-013**: The following visible UI strings MUST be moved into the message catalogue. Each is dispatched via the typed-key API; each has a translation for all four supported locales. The list is exhaustive for v1:
  - **Timer screen**: mode badges (`Focus`, `Break`, `Long Break`); state suffixes (`Paused`, `Auto-paused`, `Overtime`); control button visible labels (`Reset`, `Undo`, `Start`, `Pause`, `Resume`, `Skip session`); the corresponding verbose `aria-label` strings on each control button (each `aria-label` is its own catalogue key, distinct from the button's visible text).
  - **Sidebar nav tooltips**: `Timer`, `Statistics`, `Daily`, `Settings` (the tooltips on the four sidebar nav buttons).
  - **Settings**: all eight tab names (`General`, `Shortcuts`, `Notifications`, `Theme`, `Automation`, `Goals`, `Advanced`, `Updates`); every setting's visible label, helper / hint text, and unit suffix; the auto-save toast strings (`Settings saved`, `Failed to save settings`).
  - **Statistics view**: the four period tab labels (`Daily`, `Weekly`, `Monthly`, `Yearly`); tile labels (e.g. `Total sessions`, `Total focus time`, `Best day`, etc. — every visible tile heading); axis labels on the charts; "No data" empty-state strings.
  - **Daily view**: the header `Daily Overview`; the section header `Today's Sessions`; the empty-state `No sessions completed`.
  - **Update notification**: `Update available`, the version display surrounding string (the version number itself stays as the raw `chrono` / semver literal), `Update via Homebrew` (or the platform-specific equivalent label), `Skip release`.
  - **Tag picker / manager**: the `New tag…` placeholder string in the create-tag input; the `Choose tag` header on the tag picker dropdown.
  - **Calendar**: the twelve month names (`January` through `December`); the seven day-of-week headers (`Sun`, `Mon`, …, `Sat`).
- **FR-014**: Out of scope for v1 string extraction: `chrono`-rendered numeric date/time fragments (the digits / month-number portions); the version number literal in the update notification; the locale wire codes themselves (`en` / `de` / `it` / `tr`) — these are never user-visible. Per the 2026-05-13 clarification, date/time *formatting* per locale is deferred; the surrounding strings ARE in scope per FR-013.

#### Behaviour — Settings UI: Language dropdown (constitutional anchors III, IV)

- **FR-015**: The Settings → General tab MUST surface a new control row labelled "Language" (localised: `Language` / `Sprache` / `Lingua` / `Dil`) placed **above the existing timer-durations section** (i.e. above the `#focus-duration` field), as the first control in the tab. The control is a dropdown with selector `#locale-selector` and exactly four options in this order: `English`, `Deutsch`, `Italiano`, `Türkçe`. Order rationale: English first (source-of-truth locale per Spec A13); the remainder ordered alphabetically by native self-name (`Deutsch` < `Italiano` < `Türkçe`). Future locales insert at the deterministic alphabetical position within the non-English tail. The option labels are the native self-names of each locale and are NOT re-translated when the active locale changes (Story 1 AC 4).
- **FR-016**: The dropdown's currently-selected option MUST reflect the active locale (e.g. `Deutsch` is pre-selected when `appearance.locale == Locale::De`). Changing the selection MUST fire a handler that updates the shared `RwSignal<Locale>` in place; the existing centralized settings-persistence Effect (the debounced `Settings` autosave introduced in feature 004 and resident at the same call site that persists `theme` / `timer_theme` / `focus_duration` / etc.) MUST persist the change to disk transparently. No bespoke save-button is added; no toast specific to the language change is shown.
- **FR-017**: The new selector `#locale-selector` is the only new e2e-selector contract this feature introduces. No existing Settings → General selector (`#focus-duration`, `#break-duration`, `#long-break-duration`, `#total-sessions`, `#max-session-time`, `#sessions-per-long-break`) MAY be renamed or removed.

#### Cross-cutting (constitutional anchors II, VI, IX)

- **FR-018**: No new Tauri command is required. The settings IPC surface (`get_settings`, `update_settings`) carries the new `appearance.locale` field transparently as part of `AppearanceSettings`. If the picked library mandates a new Tauri command (which is unlikely for a purely UI-side message-catalogue dispatch), the Tauri bridge mock at `tests/e2e/fixtures/tauriMock.js` MUST be extended FIRST per AGENTS.md's mock-first discipline, then the e2e test, then the real call site. (Principle VI.)
- **FR-019**: No new network-egress path. No telemetry events. Message catalogues, locale strings, and library artefacts MUST all be bundled at compile time. (Principle II.)
- **FR-020**: The picked Leptos i18n library is a runtime Rust dependency. Its addition to `Cargo.toml` MUST be accompanied by the regenerated `Cargo.lock` in the same commit (Principle IX). If the library transitively brings in a new npm dependency (vanishingly unlikely — Leptos i18n libraries are pure Rust), `tests/e2e/package-lock.json` MUST be updated in the same commit too.
- **FR-021**: Visual regression baselines outside Settings → General MUST NOT be regenerated. The single permitted regeneration is `settings-general-chromium-linux.png`, which MUST carry a one-line PR-description note. An untouched-screen diff is a regression to fix in code — a string-extraction commit that changes the width of an English string and reflows the timer screen layout is a code regression, not a re-baseline trigger. (Principle IV.)

#### Test-first scope (constitutional anchor V)

- **FR-022**: Failing tests MUST precede implementation for the `AppearanceSettings` serde-evolution: (a) round-trip of a pre-005 JSON fixture that omits the `locale` key → deserialises to `None` (no explicit locale, triggering OS detection at cold start); (b) round-trip of a JSON fixture with each of the four `Locale` variants set as `Some(Locale)` → `Option<Locale>` wire string round-trips byte-stable (`Some(En)` ↔ `"en"`, `Some(De)` ↔ `"de"`, `Some(It)` ↔ `"it"`, `Some(Tr)` ↔ `"tr"`); (c) round-trip of a JSON fixture with an out-of-set `locale` value (e.g. `"fr"`) → falls back to `None` via `#[serde(default)]`; (d) round-trip of a JSON fixture that already contains the existing `theme` and `timer_theme` fields AND the new `locale` field → all three fields survive the round-trip. The critical invariant: `Some(Locale::En)` and `None` MUST round-trip as distinct values — they are NOT equal. UI plumbing (locale dropdown rendering, signal-binding, view re-rendering on locale change) is e2e-covered and NOT in Principle V scope (no engine state changes, no manager state machine evolves).
- **FR-023**: The locale-resolution-at-startup precedence chain (FR-009) MUST be covered by a unit-level or wasm-bindgen-test that exercises: (a) `persisted = Some(De), os = ["en-US"]` → `De` (persisted `Some(_)` wins regardless of variant, including when the persisted value happens to equal a supported OS locale); (b) `persisted = None, os = ["de-DE"]` → `De` (OS detection runs when persisted is `None`); (c) `persisted = None, os = ["fr-FR"]` → `En` (unsupported OS locale falls back to English); (d) `persisted = None, os = []` → `En` (`navigator.language` unavailable falls back to English without panicking); (e) `persisted = Some(En), os = ["de-DE"]` → `En` (explicit English choice persists — this is the critical case that the `Option<Locale>` discriminant solves; `Some(Locale::En)` MUST NOT trigger OS re-detection). The test is structural (resolution function in isolation), not a full app boot; the function MUST be extractable for testing in isolation.

#### Out-of-scope guards

- **FR-024**: No additional locales beyond the four named (`En`, `De`, `It`, `Tr`). Adding a fifth locale is its own follow-up feature.
- **FR-025**: No locale-specific date/time formatting. `chrono`-rendered timestamps stay in their existing English formatting. (Per the 2026-05-13 clarification.)
- **FR-026**: No RTL layout support. Turkish is LTR. The four supported locales are all LTR. RTL is a wholesale layout concern (mirror the entire UI grid, flip directional icons, recheck every alignment) that is OUT of scope for this feature.
- **FR-027**: No translator workflow tooling integration (Crowdin / Weblate / Lokalise / Phrase / etc.). Translation files are hand-edited in this repo; the source-of-truth keys live in the English catalogue and the other three catalogues are maintained alongside in version control.
- **FR-028**: No marketing / website / README / VISION.md string extraction. The feature is desktop-app only. Documentation, the README, the GitHub release notes, and any other repo-external surface stay English.
- **FR-029**: No automatic translation generation (LLM-driven, machine-translation-service-driven, etc.) at build time. The three non-English catalogues are hand-curated translations committed to the repo. Quality of translation is a content concern, not a runtime concern.
- **FR-030**: No per-user-defined custom locale. The user cannot supply their own catalogue file at runtime. The four bundled locales plus the English fallback are the entire selection surface in v1.

### Key Entities

> One small wire-shape evolution on an existing entity (`AppearanceSettings`), one new typed enum (`Locale`), one new in-memory message-catalogue concept (library-dependent), and one new UI control (the Language dropdown). No new on-disk entities are introduced.

- **`AppearanceSettings` (evolved, `crates/presto-ipc/src/settings.rs`)**: Gains one field — `locale: Option<Locale>` (default `None`). `#[serde(default)]` so pre-005 records (lacking the `locale` key) deserialise to `None` — the "no explicit locale chosen" sentinel. `Some(Locale)` means the user has explicitly saved a locale (any of the four variants, including English). Read by the Leptos frontend's i18n bootstrap path; the engine never reads this field; no Tauri command other than the existing `get_settings` / `update_settings` is involved.
- **`Locale` (new typed enum, `crates/presto-ipc/src/settings.rs` or sibling module)**: Four-variant closed sum type — `En`, `De`, `It`, `Tr`. Wire shape lowercase via `#[serde(rename_all = "lowercase")]`. `Default::default()` returns `En`. This is the constitution-anchored type-system encoding of the supported set (Principle III); out-of-set wire values fail serde deserialisation and fall back to the `#[serde(default)]` value.
- **Message catalogue (new, library-dependent)**: A compile-time-bundled collection of `(typed_key, locale) → string` mappings. Source-of-truth keys live in the English catalogue; the same key set exists in DE / IT / TR (per FR-006, missing keys are a build-time error). The exact file format (Fluent FTL / JSON / TOML / inline Rust macro) is a plan-level decision; the spec specifies only the contract (typed, compile-time-checked, no runtime network fetch, no on-disk catalogue outside the WASM bundle).
- **Active-locale reactive signal (new, UI-side)**: A single shared `RwSignal<Locale>` (or library-provided equivalent) seeded at app boot from the resolved cold-start locale (FR-009 precedence chain) and exposed to every translation-consuming view. Updated by the Settings → General dropdown's change handler; persisted to disk by the existing centralized settings-persistence Effect.
- **Language dropdown (UI control, Settings → General)**: A new dropdown control with selector `#locale-selector`, placed above the timer-durations section. Four options whose labels are native self-names of each locale (`English`, `Deutsch`, `Italiano`, `Türkçe`); the surrounding label string ("Language") IS localised; the option labels themselves are NOT.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: A user can switch the UI language from English to any of the three non-English locales, end-to-end, with ≤2 UI interactions (open Settings → pick from dropdown — the dropdown's change handler does the rest, no Save button to click, no app restart).
- **SC-002**: 100% of pre-005 `appearance` records (lacking the `locale` key) deserialise as `None` (no explicit locale) — measured by a round-trip test against a literal pre-005 JSON fixture, mirroring the metronome legacy fixture pattern at `crates/presto-ipc/src/settings.rs::tests::metronome_default_off`. The test MUST also assert that `Some(Locale::En)` (explicit English) and `None` (no choice) are distinct values and produce distinct cold-start resolver behaviour.
- **SC-003**: Across all four `Locale` variants, settings round-trip byte-stable through serde with lowercase wire encoding — `En` ↔ `"en"`, `De` ↔ `"de"`, `It` ↔ `"it"`, `Tr` ↔ `"tr"`.
- **SC-004**: 100% of the visible UI strings enumerated under FR-013 are dispatched through the typed-key API. Measured by a `grep`-able check that no hard-coded English string literal in those views remains outside the catalogue (the picked library will typically produce a `t!()` or `tr!()` macro call site for each translated string; views MUST use the macro, not bare string literals, for in-scope text).
- **SC-005**: 0 stringly-typed translation lookups in the codebase. Measured by the absence of any call form like `t("some.literal.key")` or `gettext("string")` — every translation lookup goes through the typed-key API (typically a `t!(KeyEnum::Variant)` proc-macro or a generated function call). Compile-time-checked: a key typo fails `cargo build` rather than rendering a placeholder at runtime.
- **SC-006**: 0 missing keys at production-build time across all four locales. Measured by the CI build failing if any non-English locale lacks a key present in the English source-of-truth catalogue. (The picked library's build-time validation is configured to fail loudly on gaps.)
- **SC-007**: Locale switching produces no perceptible mixed-locale frame. Measured by an e2e test that takes consecutive screenshots before and after a locale change; the post-change screenshot contains no string from the pre-change locale. (Implementation: Leptos signal batching produces a single re-render tick; no async barrier required.)
- **SC-008**: 0 network-egress code paths added by the i18n implementation. Measured by `grep` for `fetch(` / `XMLHttpRequest` / `reqwest::Client` / `supabase` / new external URLs in the diff — zero hits. Message catalogues are bundled into the WASM binary at compile time. (Principle II.)
- **SC-009**: Only 1 visual regression baseline is regenerated — `settings-general-chromium-linux.png`. 0 baselines outside Settings → General are regenerated. The regenerated baseline has a one-line PR note. (Principle IV.)
- **SC-010**: The cold-start locale-resolution precedence (FR-009) is deterministic across all four supported locales and all degenerate inputs (no `settings.json`, unsupported OS locale, `navigator.language` unavailable). Measured by a structural test exercising every branch of the precedence chain (FR-023).
- **SC-011**: 0 new engine code paths read from the locale signal or the message catalogue. Measured by `grep -r 'Locale\|locale\|t!\(\|tr!\(' src/src/engine/` (or equivalent for the picked library's macro names) — the engine module is locale-agnostic. (Principle I.)
- **SC-012**: 0 new Tauri commands added (FR-018). Measured by the diff against the `#[tauri::command]` attribute set in `src-tauri/src/lib.rs` showing no additions. (Principle VI.)
- **SC-013**: A user picking a non-English locale and then completing a focus session sees every visible string (mode badge, control button labels, completion-toast strings, statistics tile labels reached via post-session navigation) rendered in the picked locale — end-to-end coverage of the FR-013 surface in a single user session. Measured by an e2e test that drives the app under each of the three non-English locales and asserts the expected localised strings appear at each touched view.

## Assumptions

- **A1 — One PR, one user-facing capability**: The default delivery shape is a single PR landing the `AppearanceSettings` evolution, the message catalogue scaffolding for all four locales, the Settings → General Language dropdown, and the string-extraction work across every view enumerated in FR-013, together. The settings legacy-compat round-trip (Story 2) is the integrity guarantee that makes Story 1 safe to ship and is not split off.
- **A2 — `Option<Locale>` with `#[serde(default)]`-gated wire-shape evolution**: The new `appearance.locale` field uses `Option<Locale>` with `#[serde(default)]` (defaulting to `None`). `None` encodes "no explicit locale chosen"; `Some(Locale)` encodes "user explicitly chose this locale" (including English). This `Option<Locale>` discriminant is the resolver's authoritative "explicit vs. default" signal — value-equality against `Locale::En` MUST NOT be used as a proxy. No first-launch migration; **Principle VI** honoured at the deserialiser. A legacy `settings.json` lacking the `locale` key deserialises to `None`; on the user's first save after upgrade the resolver writes `Some(resolved_locale)` to disk, short-circuiting all subsequent launches.
- **A3 — Library pick is deferred to plan/research.md**: The spec mandates the typed-key contract (FR-005) and the compile-time-bundle contract (FR-008) but does not name the Leptos i18n library. The plan's research.md surveys at minimum `leptos-fluent`, `leptos-i18n`, `leptos_i18n_macro`, and `leptos-router-i18n`; picks one; documents the rejected alternatives. The library pick is the plan's job (Principle VIII: spec is *what + why*, plan is *how*).
- **A4 — Native self-names in the dropdown, surrounding label localised**: **[BEST-GUESS PM DECISION]** Per FR-015. The dropdown option labels (`English`, `Deutsch`, `Italiano`, `Türkçe`) stay native self-names regardless of active locale; the surrounding "Language" label IS localised. A user who accidentally lands in a locale they don't read can still pick their own language back out of the dropdown without machine-translating the option labels. Not constitutionally anchored.
- **A5 — Lowercase wire shape for `Locale`**: **[BEST-GUESS PM DECISION]** Per FR-002. Matches the existing `theme` field's lowercase string convention (`"auto"` / `"light"` / `"dark"`). Two-letter ISO-639-1 codes have no internal word boundary; kebab-case is unnecessary. Diverges from the kebab-case `AmbientSoundType` / `StatusBarDisplay` precedent because those have multi-word variants (`white-noise`, `icon-only`) where kebab-case carries information. Not constitutionally anchored.
- **A6 — Locale switching is signal-batched, not async-loaded**: Per FR-007. All four locales' catalogues are resident in WASM memory after init. Switching is a constant-time signal flip; no `await` step, no loading spinner, no transient empty state. The picked library's documentation will confirm whether this is its default mode (most Leptos i18n libraries are signal-driven by design); if not, the library is configured to operate in that mode.
- **A7 — OS-locale detection is a P3 nice-to-have**: Per User Story 4. The brief explicitly lists OS detection as part of the resolution chain (FR-009), but framing it as P3 means: if implementation complexity gates it (e.g. the picked library has no clean hook for "seed the active-locale signal from a runtime-computed value"), Story 4 can be deferred to a follow-up and the feature ships with: explicit-pick-from-Settings + English-default. P1 stories (1 and 2) deliver full value even without OS detection.
- **A8 — Mixed-language rendering of date/time + surrounding strings**: Per the 2026-05-13 clarification. A DE user MAY see `Wöchentlich` (the period tab label) above `Mon, May 13` (the chrono timestamp) on the statistics view. Per-locale `chrono` formatting is OUT of scope for v1. Acceptable tension; revisit in a follow-up if user feedback objects.
- **A9 — Translation-coverage `(beta)` indicator is conditional**: Per User Story 5 / FR-006. If all four locales reach 100% coverage at ship time, the `(beta)` badge feature is omitted entirely (no code, no UI). If any locale ships with gaps, the badge appears next to that locale's option label. P3 because it is purely informational.
- **A10 — String width drift is fixed by container-side robustness, not per-locale tweaks**: Per the Edge Cases entry. German strings are typically ~30% longer than English; Turkish has long agglutinative compounds. Layout MUST tolerate this — controls do not clip, do not overflow. If the English baseline drifts (e.g. a container's intrinsic-size measurement leaks the longest non-English string), that is a regression to fix in the container's sizing logic, not absorbed by re-baselining (FR-021 / Story 3 AC 3). **[BEST-GUESS PM DECISION]** No per-locale CSS overrides are introduced.
- **A11 — `aria-label` strings are catalogue entries distinct from visible button labels**: Per FR-013 and the Edge Cases. The verbose `aria-label` (e.g. "Reset the timer to the start of the focus session") is a separate catalogue key from the visible button text ("Reset"). Both are compile-time-checked. Not constitutionally anchored beyond Principle III's typed-key insistence.
- **A12 — Settings persistence inherits from feature 004's centralized Effect**: Per FR-016. The Language dropdown's change handler updates `settings.notifications.locale`... wait — `settings.appearance.locale`. The existing debounced autosave Effect picks up the change and persists it without bespoke save-button wiring. The pattern is identical to how feature 004's `ambient_sound_*` toggles persist today.
- **A13 — Source-of-truth catalogue is English**: Per FR-006 and the brief. The English catalogue defines the key set; the DE / IT / TR catalogues track it. A key added to English-only and never propagated is a build-time failure (FR-006). A key removed from English MUST also be removed from the other three (a stale key in DE is also a build-time failure under most candidate libraries' validators). The asymmetry is deliberate — English is the source-of-truth locale.
- **A14 — Visual regression budget is one baseline (settings-general)**: Per User Story 3 / FR-021 / SC-009. The widening is gated by a per-baseline justification note in the PR description. Principle IV honoured by explicit policy. The non-Settings-General baselines stay captured in English and stay locked; per-locale baselines are out of scope (Clarifications resolved 2026-05-13).
- **A15 — No engine `web_sys` imports introduced**: Per Principle I. The i18n implementation lives entirely in the Leptos frontend's view layer and settings-bootstrap layer, never in `src/src/engine/`. The OS-locale detection (FR-009 step 2) calls `web_sys::window().navigator().language()` from the bootstrap path (`src/src/app.rs`-ish), not from the engine module. Measured by SC-011.
- **A16 — Strict static analysis posture continues to apply**: Per Principle X. New code is clippy-pedantic-clean; no `#[allow(...)]` without inline justification. The picked library's generated code (proc-macro output) MUST also pass the clippy-pedantic posture in CI — if the picked library's macro-generated code triggers pedantic lints, the library is either reconfigured (most have lint-quieting attributes baked in) or rejected at plan time in favour of one that doesn't.
